# 票据投递回执台设计

名单快照由收件人、渠道版本、批次内别名和截止时间构成，其配置哈希在工作区首次导入时冻结。投递 JSONL 以消息 ID、尝试号形成事件身份；同身份异内容进入冲突队列。原始行、来源文件和 SHA-256 留存。

数据流：冻结名单 → 投递事件导入 → 批次内地址归并 → 每消息状态重建 → 截止时效与撤回重发判断 → 逐人结论 → JSON/Markdown 送达证明。

每个消息从 `queued` 开始，可走 `sent`、`deferred`、`bounced`、`receipt` 或 `revoke` 的合法转移。无排队事件或非法跳转标记问题；回执事件时间晚于截止点标记 `late_delivery`。新消息的 `resends` 必须引用已出现的旧消息，旧退信事件继续保留。收件人可能有多个批次内别名，但未知地址不得自动归并到其他人。

结论为 `effective`、`undelivered`、`insufficient`；缺送达时间或状态证据不能推定有效。业务问题与结论可重算，原始投递史不可覆盖。当前只处理本地模拟投递日志，不发送真实通知。

## 实体标签发行

物理设备层（`print_lab`）只暴露每枚序列的 `blank/jammed/printed/void` 状态、修订号，以及带故障注入的比较交换动作。发行层（`issuance`）把设备当唯一事实来源，但只在业务合同允许时才采信它。

工单开案时冻结：真实 `queued` 事件 ID/身份/事件 SHA、来源 ID/来源 SHA、通知 ID、版面版本与由 `label-v1` 规范串计算的版面摘要。打印前再次核对来源与冻结名单，未知收件人、重复通知、旧版面、身份冲突都不会占用实物标签。

持续性由三张账保证：`label_job`（工单意图与冻结证据）、`label_assignment`（每枚序列与工单的归属、序号、状态、设备修订）、`label_operation`（幂等操作 ID 与意图/结果）。设备动作前先落意图，动作后按实况对账；重启时 `recover_case` 只读设备：已打印则接管（含 ACK 丢失），已作废则确认，卡纸则记废标，空白则把意图回退为可重试。相同操作 ID 重放返回既有结果，不重复打印、作废或收费。

标签槽位与序列归属是两个约束：每个工单同时最多一枚当前有效标签（部分唯一索引），每枚序列至多归属一个工单（主键），卡纸/作废序列永久消耗。`mail_ready` 需要设备归属 + 内容摘要吻合 + 邮资入账三者同时成立；`queued` 从不等于送达，`decision` 保持原样。

两套合同在同样设备故障下得到不同但都正确的实物账：`retain_verified_serial` 保留已打印的 L100（核验后），J2 用 L102；`void_and_reissue` 作废 L100 取回执后给 J1 打 L103，J2 仍用 L102。作废 ACK 丢失时先读 L100 实况，未确认作废前禁止重打，确保 L100 与 L103 不会同时可交邮。

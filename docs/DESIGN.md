# 票据投递回执台设计

名单快照由收件人、渠道版本、批次内别名和截止时间构成，其配置哈希在工作区首次导入时冻结。投递 JSONL 以消息 ID、尝试号形成事件身份；同身份异内容进入冲突队列。原始行、来源文件和 SHA-256 留存。

数据流：冻结名单 → 投递事件导入 → 批次内地址归并 → 每消息状态重建 → 截止时效与撤回重发判断 → 逐人结论 → JSON/Markdown 送达证明。

每个消息从 `queued` 开始，可走 `sent`、`deferred`、`bounced`、`receipt` 或 `revoke` 的合法转移。无排队事件或非法跳转标记问题；回执事件时间晚于截止点标记 `late_delivery`。新消息的 `resends` 必须引用已出现的旧消息，旧退信事件继续保留。收件人可能有多个批次内别名，但未知地址不得自动归并到其他人。

结论为 `effective`、`undelivered`、`insufficient`；缺送达时间或状态证据不能推定有效。业务问题与结论可重算，原始投递史不可覆盖。当前只处理本地模拟投递日志，不发送真实通知。

## 终态因果裁决

同一消息同时出现 `receipt` 与 `revoke` 两个终态时，不按导入顺序裁决，而按批次配置的 `adjudication` 契约形成因果结论。`event_time`（事件时间优先）在设备时间自洽（同一设备随序号推进时钟不回退）且时间戳可区分时，以业务发生时间裁决；`relay_seq`（接收端序号优先）仅当同一 relay 的单调序号连续、尝试链闭合且二者同向时采用接收端序号，其他情况待核。裁决记录保留两事件的原始时间、设备序号、接收端序号、来源行与消息尝试关系，两轴矛盾时记录 `causal_contradiction` 供审计。

时钟漂移、重复终态、回执引用断裂的尝试链、撤回跨越重发边界一律进入证据不足，不自动形成有效/未达结论；迟到文件的导入顺序不作为真实先后。证据只归属各自 attempt：重发不抹掉旧消息的失败史，旧消息的迟到回执也不反向替代重发的回执。撤回若被证明先于回执，则判撤回后无有效送达（`undelivered`）；回执若被证明先于撤回，则保留撤回史并判 `effective`。

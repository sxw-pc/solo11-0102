# 票据投递回执台设计

名单快照由收件人、渠道版本、批次内别名和截止时间构成，其配置哈希在工作区首次导入时冻结。投递 JSONL 以消息 ID、尝试号形成事件身份；同身份异内容进入冲突队列。原始行、来源文件和 SHA-256 留存。

数据流：冻结名单 → 投递事件导入 → 批次内地址归并 → 每消息状态重建 → 截止时效与撤回重发判断 → 逐人结论 → JSON/Markdown 送达证明。

## 有界内存的来源快照

来源可能远大于内存。导入按固定 `chunk_size` 读取、增量解码（`utf-8-sig` 仅剥离首个 BOM）、增量切行并分块哈希；Python 进程只保留当前块、一行残余和一条待提交记录，`source.raw` 由暂存块用 SQLite 增量 blob 写入，峰值内存随块大小而非文件长度增长。

每次尝试把字节、哈希和解析结果写入一次性暂存表（`stage_snapshot/stage_chunk/stage_event/stage_issue`），完成后在同一次事务中把暂存块复制进 `source.raw`（复制时重算 SHA-256 比对）、写入 `event`/`issue` 并记录 `import_audit`。崩溃只可能留下暂存草稿，绝不会留下半份正式 source 或重复事件；完整的暂存快照以同一快照身份被重试复用。

入站逻辑路径在读取途中被原子替换时，须显式选择一种合同：

- `freeze_on_open`：以打开时固定的文件描述符为准，忽略路径替换，提交打开时的完整原版。
- `verify_then_retry_latest`：读完发现路径版本变化则丢弃该次暂存，对最终稳定版本重试并只提交该版本。

任一合同下 `source.raw`、记录哈希与全部 `event` 都来自同一完整版本，不会混用两个版本；同一快照按源哈希幂等，异内容同身份仍进入现有冲突隔离。


每个消息从 `queued` 开始，可走 `sent`、`deferred`、`bounced`、`receipt` 或 `revoke` 的合法转移。无排队事件或非法跳转标记问题；回执事件时间晚于截止点标记 `late_delivery`。新消息的 `resends` 必须引用已出现的旧消息，旧退信事件继续保留。收件人可能有多个批次内别名，但未知地址不得自动归并到其他人。

结论为 `effective`、`undelivered`、`insufficient`；缺送达时间或状态证据不能推定有效。业务问题与结论可重算，原始投递史不可覆盖。当前只处理本地模拟投递日志，不发送真实通知。

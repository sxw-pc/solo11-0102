# 票据投递回执台设计

名单快照由收件人、渠道版本、批次内别名和截止时间构成，其配置哈希在工作区首次导入时冻结。投递 JSONL 以消息 ID、尝试号形成事件身份；同身份异内容进入冲突队列。原始行、来源文件和 SHA-256 留存。

数据流：冻结名单 → 投递事件导入 → 批次内地址归并 → 每消息状态重建 → 截止时效与撤回重发判断 → 逐人结论 → JSON/Markdown 送达证明。

每个消息从 `queued` 开始，可走 `sent`、`deferred`、`bounced`、`receipt` 或 `revoke` 的合法转移。无排队事件或非法跳转标记问题；回执事件时间晚于截止点标记 `late_delivery`。新消息的 `resends` 必须引用已出现的旧消息，旧退信事件继续保留。收件人可能有多个批次内别名，但未知地址不得自动归并到其他人。

结论为 `effective`、`undelivered`、`insufficient`；缺送达时间或状态证据不能推定有效。业务问题与结论可重算，原始投递史不可覆盖。当前只处理本地模拟投递日志，不发送真实通知。

## 外部渠道披露

内部证据报告（地址、逐人渠道、payload、来源路径、送达证明）保持完整，只对独立授权的内部审计员开放。对外披露走单独路径：从冻结名单读取每位收件人的渠道，只把目标渠道的计数写入外部文件；不读取或重判 receipt/revoke、有效送达 decision 或消息 attempt。

发布台账按受众独立保存每次实际发布的集合、计数、文件摘要、请求 ID、策略与状态。拟发布前，把该受众所有已发布等式与新等式联立，每人 v2 归属为二元变量；只要任一变量被唯一推出就阻止原集合。该检查覆盖三组以上重叠群组、全零/全一、单人群组与矛盾历史，不能退化为“每组至少两人”或“只比最新两组”。拒绝的请求与其他受众的内部报告不进入该受众可见知识。

`minimum_safe_coarsening` 从 `allowed_expansion` 中枚举最少新增成员，发布实际扩大的集合并记录原请求集合；`deny_unsafe` 只接受原集合。相同请求 ID 重放返回既有发布而不产生第二份文件或第二笔台账。同受众的发布在 `BEGIN IMMEDIATE` 内读取历史、写入 pending 行，再原子替换文件并置为 published；`recover-disclosures` 会补全 pending 行、修正摘要不符的文件并删除无台账记录的孤儿文件，因此不会出现已发文件无记录或记录指向另一份文件。
